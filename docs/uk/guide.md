## Встановлення та межі

Встановіть проєкт із робочої копії командою `python3 -m pip install .` у віртуальному середовищі. Підтримується Python 3.11+. Крім Python, залежностей часу виконання немає. `assist-lab --help --lang en` показує команди; також працюють `ru`, `de` та `es`. Запуск через модуль — `python3 -m assist_scenario_lab`.

Завантаження файлів потребує прапорців ОС `O_NOFOLLOW` і `O_NONBLOCK`, доступних у Linux та macOS. Якщо хоча б одного немає, CLI повертає код 2 з `unsupported_platform` до відкриття входу. Python API для оцінювання та імпорту даних у пам'яті цих прапорців не потребує.

Це автономний аналізатор, а не прошивка голосового супутника, акустичний детектор, збирач даних наживо, інтеграція HA чи повний бенчмарк. Справжні користувацькі приймальні випробування продукту проводьте відповідними засобами прошивки. Передавайте отримані докази обмеженого обсягу цьому інструменту лише після перевірки конфіденційності.

## Канонічний вхід

Почніть із `examples/synthetic-pass.json`. Корінь потребує `schema: assist-scenario-lab/v1`, булевого `synthetic`, об'єкта `requirements` та від 1 до 500 `sessions`. Невідомі поля відхиляються. Сесія має унікальний `id`, а також `platform`, `scenario`, `clock`, `events` і `checks`. Ідентифікатори містять 1–64 літери ASCII, цифри, підкреслення або дефіси; починаються з літери чи цифри. Використовуйте псевдоніми, а не назви кімнат, адреси чи ідентифікатори пристроїв.

`clock` має значення `relative_monotonic` або `utc_derived`. Події містять `stage`, `at_ms`, `origin`. Часові значення скінченні, невід'ємні, не перевищують 12 годин і впорядковані неспадно. Перша подія — `request` у нульовий момент. Кожен етап трапляється один раз. Підтримувані етапи: `request`, `wake_detected`, `stt_end`, `intent_end`, `tts_ready`, `protocol_end`, `playback_started`, `playback_finished`, `audible_start`, `error`. Різні конвеєри можуть працювати потоково; тому, окрім хронологічних позначок часу, навмисно немає фіксованого порядку між TTS та відтворенням.

Джерела — `pipeline`, `satellite`, `operator` та `acoustic`. Лише `operator` або `acoustic` можуть бути джерелом `audible_start`. Кожна сесія має надати всі три перевірки: `intent_correct`, `action_observed`, `audible`. Кожна містить `result` (`pass`, `fail`, `unknown`) та `method`. Невідомий результат потребує `none`. Інші дозволені методи: `operator`/`intent_assertion` для наміру, `operator`/`ha_state` для дії та `operator`/`acoustic` для чутності. Часова позначка чутного звуку потребує успішної перевірки чутності. Інструмент перевіряє узгодженість, а не істинність.

Вимоги можуть увімкнути будь-яку з трьох перевірок та необов'язковий `max_audible_ms`. Пропущені або хибні перевірки не обов'язкові: політика лише для API може пройти без фізичних доказів і має бути так позначена. Комплектні приклади потребують усіх перевірок. Помилка конвеєра завжди означає провал. Відсутність `protocol_end` означає неповноту. Провал обов'язкової перевірки переважає невідомі спостереження. Затримка понад поріг означає провал; відсутня обов'язкова затримка — неповноту.

## Імпорт запуску HA

Адаптер приймає один **масив об'єктів подій**, а не повний журнал WebSocket або діагностичний ZIP. Локально витягніть тіло кожної події. Об'єкти містять рівно `type`, `timestamp`, `data`; дані можуть бути об'єктом або null. Часові позначки мають відповідати ISO 8601 із часовим поясом. Починайте з `run-start`, зберігайте хронологічний порядок і не змішуйте запуски. Повторні зіставлені етапи відхиляються.

```sh
assist-lab import-ha examples/ha-events.synthetic.json --session demo --platform demo --synthetic > /tmp/imported.json
assist-lab evaluate /tmp/imported.json --format json
```

Друга команда навмисно повертає 3. `run-end` перетворюється на `protocol_end`, а не фізичний успіх. `tts-end` перетворюється на `tts_ready`, а не чутний звук. Усі `data` відкидаються, зокрема розшифрування мовлення, вхідний текст, помилки, URL/токени TTS та метадані конвеєра. Події початку, прогресу та VAD розпізнаються, але не зберігаються. Перетворені часи використовують `utc_derived`: віднімання показів звичайного годинника не є монотонним вимірюванням затримки й залежить від коригування годинника. Усі три фізичні/семантичні перевірки лишаються невідомими.

## Звіти та порівняння

`--format text|json|html|junit` обирає звіт. Переспрямування оболонки записує результат у вибраний локальний шлях. Сам CLI ніколи не перезаписує вхід. Коди виходу: 0 — записані вимоги виконано; 1 — провал; 2 — некоректний вхід/аргументи; 3 — неповнота. JUnit представляє неповні сесії як пропущені; CI все одно має враховувати код 3.

JSON групує за платформою, сценарієм, годинником і методом вимірювання чутного звуку. Ніколи не вважайте різні годинники або людські й акустичні спостереження взаємозамінними вимірюваннями. p50/p95 використовують найближчий ранг. За менш ніж 20 зразків p95 дорівнює null; 20 — поріг звітування, а не доказ статистичної впевненості. Невдалі сесії зі спостереженим звуком залишаються у вибірці затримки, а кількість їхніх провалів — видимою. Не відбирайте лише успішні спроби. Сире аудіо та розшифрування не експортуються. Ідентифікатори все одно можуть розкривати дані, тому перевіряйте їх.

HTML перелічує всі сесії та будує графік перших 50 чутних спостережень у спільному масштабі. Читайте платформу й метод кожного рядка; огляд не є статистичним рейтингом. `evidence_verified: false` присутнє завжди. `synthetic: false` означає, що автор не позначив запуск синтетичним, а не що обладнання незалежно перевірено.

## Збирання змістовних доказів

Перед спробою визначте очікуваний намір і ціль. Послідовно задавайте стартову подію: запит конвеєра не обов'язково є початком вимовленої фрази. Ведіть окремий журнал випробувань із версіями ПЗ, мовою, умовами мережі, розміщенням мікрофона й динаміка, методом спостереження та кількістю спроб. Для точного часу чутного звуку використовуйте відповідне акустичне вимірювання; не підміняйте його першим мережевим фрагментом. Записуйте провали, таймаути й відсутні докази. Пакет не виконує акустичної синхронізації та не керує згодою на запис.

## Усунення несправностей

- `object_fields`: порівняйте ключі з канонічними тестовими даними; повний діагностичний дамп не приймається.
- `ha_timestamp` / `time_order`: експортуйте один запуск, додайте часові пояси, перевірте корекції годинника. Не переставляйте події для штучного отримання затримки.
- `stage`: етап невідомий або повторний; перевірте, чи не об'єднано два запуски.
- `audible_origin` / `conflicting_audible`: метадані відтворення не замінюють чутний звук.
- Код 3 після успішного API: очікується, доки не записано обов'язкових спостережень.
- `unsupported_platform`: в ОС немає `O_NOFOLLOW` або `O_NONBLOCK`; використовуйте середовище з обома прапорцями (Linux чи macOS). Вхід відхиляється до відкриття, перевірки символічних посилань або FIFO не послаблюються.
- `file_size_type`: лише звичайний JSON UTF-8 до 2 MiB. Каталоги, FIFO та символічні посилання в останньому компоненті відхиляються. Посилання в батьківських каталогах не є межею пісочниці.
- `number`: часові значення не можуть бути від'ємними, нескінченними, булевими або перевищувати 12 годин.

Помилки виводять перекладене пояснення та стабільний код, а не вміст джерела чи локальні шляхи. Публічні приклади цілком синтетичні. Зберігайте експорти поза цією робочою копією, бажано у приватному тимчасовому каталозі.

## Архітектура, переклади та джерела

![Автономний потік даних](../../assets/architecture.svg)

`core.py` виконує чисту валідацію, імпорт і оцінювання; `cli.py` формує формати; `locales/*.json` містить чотири словники. Тести вимагають відповідності ключів словників. Машинні ключі та діагностичні коди не перекладаються. Повні посібники охоплюють 24 мови документації ha-homelab; CLI та README залишаються англійською, російською, німецькою й іспанською. Додавайте довідкові переклади з перевірками відповідності та перевіреними прикладами.

Зіставлення протоколу перевірено за [документацією Home Assistant Assist](https://developers.home-assistant.io/docs/voice/pipelines/) та [моделями подій HA 2026.10.0](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/components/assist_pipeline/models.py). Життєвий цикл супутника описано в [офіційному посібнику сутності](https://developers.home-assistant.io/docs/core/entity/assist-satellite/). Ці upstream API не обіцяють акустичної перевірки; її відокремлення тут є проєктним рішенням.
